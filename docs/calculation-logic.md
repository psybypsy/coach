# 計算邏輯總覽

這份文件把報告系統裡**所有會算出數字的地方**攤開來：公式是什麼、為什麼這樣設計、
邊界怎麼處理、以及前後端在哪裡各有一份實作（改一邊要記得改另一邊）。

所有公式都對照過實際程式碼，不是設計稿。

---

## 0. 一張圖看懂資料怎麼流動

```
學員填 T0（0–10）
      │  ①換算
      ▼
  valence（−100 ~ +100）◄──② AI 依週記文字評分
      │
      ├──③ 分級 → Level 1–5
      ├──④ 與 T0 相差幾個百分點 → 雷達圖軸標籤
      └──⑤ 統計 → 平均／最高最低／變化／最強面向
```

**valence 是整個系統的共同單位。** 不管來源是學員自填的 T0，還是 AI 讀完週記給的分數，
一律先換算成 −100 ~ +100，之後所有圖表、分級、比較都建立在這個尺度上。

---

## ① T0 起始分數：0–10 → valence

學員在第一次登入時，用滑桿為五個面向各填 0–10。

```
valence = round((分數 − 5) × 20)
```

| 學員填 | valence | 意義 |
|---|---|---|
| 10 | +100 | 上限 |
| 8 | +60 | |
| 5 | 0 | 中性 |
| 3 | −40 | |
| 0 | −100 | 下限 |

**為什麼是這個公式**：學員的直覺尺度是 0–10（5 分是「還好」），而系統內部要用
有正負號的 −100 ~ +100（0 才是中性）。`(x−5)×20` 把 5 對齊到 0，並把 0–10 線性拉開到滿刻度。

**邊界處理**：輸入先夾在 0–10 之間；非數字（None、空字串）當成 5 分（中性），
不會讓圖表爆掉。

> 兩份實作：後端 `_baseline_valence()`、前端 `baselineToValence()`。

---

## ② valence 本身：AI 評分

valence **不是計算出來的，是 AI 讀完該週文字後判定的**，範圍 −100 ~ +100，0 為中性。
每個分數都要求 AI 附上引用原話的理由。

**程式端的防線**：`_clamp_v()` 會把回傳值強制轉成整數並夾在 −100 ~ +100；
非數字一律當 0。所以就算模型回傳 "很高" 或 999，也不會污染後面的計算。

> ⚠️ **已知偏差**：實際資料（140 個面向分數）中位數 +60、平均 +58.7，
> 63% 落在 ≥+60。AI 傾向給正分。這不影響公式正確性，但解讀時要知道
> 「Level 5」在目前資料裡並不稀有。

---

## ③ 分級：valence → Level 1–5

用**語意門檻**（以 0 = 中性為錨點）而不是照分佈切，這樣同一個分數永遠對應同一個等級，
跨學員、跨週次才能比較。

| valence | 等級 | 內部描述（不對外顯示） |
|---|---|---|
| ≥ +60 | **Level 5** | 充沛 |
| +20 ~ +59 | **Level 4** | 穩定 |
| −19 ~ +19 | **Level 3** | 中性 |
| −20 ~ −59 | **Level 2** | 低落 |
| ≤ −60 | **Level 1** | 明顯低落 |
| 該面向沒寫 | **這週較少著墨** | — |

**「沒寫」與「寫了但低落」刻意分開**：兩者的教練意涵完全不同，
不能都塞進 Level 1。

### 單週報告 vs 跨週分析用哪個分數

| 情境 | 取值 |
|---|---|
| 學員單週報告（只有 1 週資料） | 就用那一週 |
| 教練跨週分析（N 週資料） | **取全期平均** |

跨週為什麼不用最後一週：某面向前七週都是 −70、最後一週衝到 +85，
用末週會標成 Level 5，與內文的跨週結論互相矛盾。取平均（−50.6 → Level 2）才符合實際樣態。
只平均「有資料」的週次；全部沒資料才回「這週較少著墨」。

### 為什麼要在後端強制校正

prompt 已經寫明對應表，但**不能只靠 AI 自律**。實測資料裡出現過：

- 同一個 +80 分被寫成「充沛」「穩定」「正在萌芽」三種
- 6 筆直接把提示詞「飽滿度」當標籤印出來

所以 `_normalise_level_labels()` 會在解析完 AI 回應後，**依分數重寫小標上的等級**。
它用 regex 只鎖定「`- **字母（中文）：詞**`」這個形狀，
不會動到子條列、優勢小標、金句或參考文獻。

> 兩份實作：後端 `valence_level()` / `valence_level_number()`、
> 前端 `vLabel()` / `vLevel()`。**改一邊必須同步改另一邊**，
> 目前用 11 個測試點驗證兩邊輸出完全一致。

## ④ 雷達圖的變化幅度：提高了幾個百分點

雷達圖每個字母旁會標 `P +48%` 這樣的變化幅度。

```
水位(%) = (valence + 100) ÷ 2        ← 把 −100~+100 攤平成 0~100%
變化    = round(本期水位 − T0 水位)
```

例：T0 填 3 分 → valence −40 → 水位 30%；本週 +55 → 水位 77.5% → 標示 **+48%**

**為什麼不用相對成長率**：起點可能是負數或 0（T0 填 5 分 → valence 0），
相對成長率會算出 −237% 或除以零這種沒有意義的數字。改用「百分點差」永遠有意義。

持平時顯示「持平」而不是 `+0%`。

> 兩份實作：後端 `_pct_change_label()`、前端 `pctChangeLabel()`。

## ⑤ 摘要統計（四個數字）

以 `sessions` 陣列（含 T0 當第 0 筆）計算：

| 指標 | 公式 |
|---|---|
| 平均整體 valence | `round(所有 overall 的平均)` |
| 變化（末 − 首） | `最後一筆 overall − 第一筆 overall` |
| 最高 / 最低 | `max(overall)` / `min(overall)` |
| 最強面向 | 各面向**跨全部週的平均**最高者 |

**注意**：T0 會被當成「第 0 筆」接在最前面，所以「變化（末−首）」實際上是
「最新一週 − T0 起點」，這正是想看的東西。

情緒相關的圖（正負情緒平衡、詞雲）**不含 T0**，因為 T0 只有分數、沒有文字與情緒詞。

> 實作：前端 `chartData()`。

## ⑥ 主題占比：正規化成總和恰好 100

AI 為六類主題（工作／關係／健康／休息／成長／其他）各給一個權重，程式再正規化：

```
1. 每個值取 max(0, 數值)      ← 負數與非數字都歸零
2. total = 六個值相加
3. total ≤ 0  → 直接回「其他 100%」
4. 否則各項 = round(值 × 100 ÷ total)
5. 四捨五入後可能是 99 或 101 → 誤差補到「原始權重最大」的那一項
```

**第 5 步是關鍵**：六個數字各自四捨五入後不保證加起來剛好 100。
把誤差補到最大的那一項，視覺上最不明顯，而且保證圓餅圖永遠是完整的一圈。

> 實作：後端 `_normalise_topic_shares()`。

## ⑦ 情緒詞雲：字級與正向佔比

**字級**（15 ~ 43 px）：

```
t    = (該詞次數 − 1) ÷ max(1, 最高次數 − 1)     ← 正規化到 0~1
抖動  = 由詞本身雜湊出的 0~1 固定值
字級  = 15 + t × 21 + 抖動 × 7
```

抖動是**由文字內容決定的固定值**（不是亂數），所以同一個詞每次重畫大小都一樣，
不會每次重新整理就跳動；但不同詞之間有變化，看起來才像詞雲而不是整齊的階梯。

**排列**：先依次數排序，再交替往左右兩端擺（`i % 2` 決定 push 或 unshift），
讓最常出現的詞落在正中央。

**正向佔比**：

```
正向佔比 = round(正向詞數 ÷ (正向詞數 + 負向詞數) × 100)
```

分母**刻意排除中性詞** —— 要看的是「正負之間的傾向」，中性詞會稀釋這個訊號。
正負都是 0 時回傳 50（中間值）。

> 實作：前端 `emotionWordCloud()`。

## ⑧ 正負情緒平衡（上下柱狀圖）

每一週分別數出正向詞與負向詞的**個數**（不是強度加總），正向往上、負向往下。

```
柱高比例 = 該週的數量 ÷ max(1, 全部週次裡的最大值)
```

用全期最大值當基準，所以各週之間的高度可以直接互相比較。

> 實作：前端 `affectBalance()`。

## ⑨ 課程週次：日期 → 第幾週

```
第 1 週：2026-07-27 ~ 2026-08-09   ← 刻意拉長兩個日曆週（起跑緩衝期）
第 2 週起：2026-08-10 開始，每七天一週

week = 1                                   若日期 < 2026-08-10
week = (日期 − 2026-08-10) ÷ 7 + 2         否則
```

| 日期 | 第幾週 |
|---|---|
| 7/27、8/3 | 第 1 週 |
| 8/10 | 第 2 週 |
| 8/17 | 第 3 週 |
| **8/24** | **第 4 週 ← 教練審核週** |
| 8/31 / 9/7 / 9/14 | 第 5 / 6 / 7 週 |
| **9/21** | **第 8 週 ← 教練審核週** |

**第 1 週為什麼拉長**：這梯次 8/1 才開始加入白名單，讓當週或次週開始寫的人
都算第 1 週，不會因為晚幾天加入就少一週。

課程起始日之前的日期會算出 ≤ 0，系統直接擋掉（回 400），不產生報告。

> 實作：後端 `_program_week_number()`、`_program_week_bounds()`。

## ⑩ 教練分析何時該重跑：落後判斷

自動重跑**不是每次都跑**（會一直花 AI 費用），而是先用兩次輕量查詢判斷是否落後：

```
落後 =  沒有 coach_analyses 那一列                ← 從沒分析過
     或 有那列但 sessions 是空的                  ← 只存過 T0
     或 based_on < 實際週記數                     ← 有新的一週還沒進去
```

`based_on` 記的是上次分析涵蓋幾週。**用「落後與否」當門檻，而不是「有沒有新增報告」**：
報告可能早就存在（學員重複觸發、或由別的路徑補產生），那時仍然需要重跑。

只有真的落後才會呼叫 AI；已是最新就直接返回，不花錢。

> 實作：後端 `_coach_analysis_state()`。

## 需要特別留意的三件事

### 1. 有六組計算是「前後端各一份實作」

| 計算 | 後端 | 前端 |
|---|---|---|
| T0 換算 | `_baseline_valence()` | `baselineToValence()` |
| 分級 Level 1–5 | `valence_level()` | `vLabel()` / `vLevel()` |
| 變化百分點 | `_pct_change_label()` | `pctChangeLabel()` |

**改任何一邊都必須同步改另一邊**，否則學員在網頁看到的和 PDF 收到的會不一致。
程式碼註解裡都有寫明這件事。

### 2. 校正只在「產生報告當下」執行

改了分級規則之後，**資料庫裡的既有報告不會自動更新**。
要套用新規則必須重新生成（會產生 AI 費用）。

### 3. AI 給的分數偏正

中位數 +60。這代表 Level 5 在目前資料中很常見，解讀時不要當成「罕見的高分」。
若要提高鑑別度，該調整的是**評分 prompt**（要求真正用滿 −100~+100），
而不是移動分級門檻——門檻一動，過去的報告就無法跟未來的比較。
